# 決定の多様性を体験するアプリ — リキッド・デモクラシー シミュレーター 設計書

## 1. 背景・目的

「決定の多様性を体験するアプリ」の第一弾として、リキッド・デモクラシー(Liquid Democracy)のシミュレーター/デモツールを作る。

将来的に、ソーティション、クアドラティック・ファンディング、ストアブル・ボーティングなど他の意思決定メカニズムも追加していく前提のため、最初のメカニズムを「差し替え可能なモジュール」として実装し、拡張の土台とする。

- 想定用途: チーム/企業での意思決定に馴染むメカニズムを、管理者(1名)が仮想シナリオを組んで見せる**シミュレーション/デモツール**。実際の参加者がログインして投票する運用ではない。
- 想定規模: 5〜20人程度の人物、複数トピック。
- データ永続化: 不要。ブラウザを閉じたら消えてよい(セッション中のみ保持)。

## 2. スコープ

### 含む
- 管理画面: 人物(名前・専門分野タグ)、トピック(タイトル・説明)の追加/編集/削除
- 管理画面: 人物×トピックのマトリクスで、各人物が各トピックについて「直接投票(賛成/反対/中立)」するか「他の人物に委任」するかを設定
- 委任チェーンの解決(多段委任、循環検出)
- 結果画面: トピックごとに
  - 投票集計(賛成/反対/中立/未確定の円グラフ・棒グラフ)
  - 委任ネットワークグラフ(誰が誰に委任したか、最終stanceで色分け、循環は強調表示)
  - 直接投票 vs 委任の割合

### 含まない(将来の拡張候補)
- リキッド・デモクラシー以外の6つのメカニズム(ソーティション、リキッド・アセンブリー、QF、ストアブル・ボーティング、フューチャーラシー、熟議民主主義)
- ユーザー認証・複数管理者・実運用向けの参加者ログイン
- データの永続化(DB/ファイル保存)
- 大規模人数(数百人規模)向けのグラフ最適化

## 3. データモデル

```typescript
type Stance = "agree" | "disagree" | "neutral";

interface Person {
  id: string;
  name: string;
  expertiseTags: string[]; // 例: ["教育", "AI"]
}

interface Topic {
  id: string;
  title: string;
  description?: string;
}

interface Ballot {
  personId: string;
  topicId: string;
  mode: "direct" | "delegate";
  stance?: Stance;       // mode === "direct" の場合のみ
  delegateTo?: string;   // mode === "delegate" の場合のみ(personId)
}
```

- `Ballot` は人物×トピックの組ごとに高々1件(存在しない場合は「未設定」= 結果集計上は「未確定」として扱う)。
- 状態は React Context + useReducer でアプリ内メモリに保持する。永続化なし。

## 4. 委任解決ロジック

トピックごとに、各人物の最終 stance を以下の手順で解決する(純粋関数として実装し、`mechanisms/liquidDemocracy/resolveDelegation.ts` に置く)。

1. 起点となる人物からスタートし、訪問済みノード集合を用意する。
2. その人物の `Ballot` が `mode: "direct"` なら、その `stance` を最終結果として確定。
3. `mode: "delegate"` なら、`delegateTo` の人物へ遷移。既に訪問済みのノードに戻った場合は**循環**と判定し、その循環に含まれる全員を `resolved: "circular"` として記録する。
4. `delegateTo` が指す人物が存在しない、または該当トピックの `Ballot` が未設定の場合は `resolved: "unresolved"` として記録する。
5. 全人物について解決した結果を `Map<personId, ResolvedStance>` として返す(`ResolvedStance` は `Stance | "circular" | "unresolved"`)。
6. 結果画面ではこの解決結果を集計し、賛成数・反対数・中立数・(circular + unresolved をまとめて)未確定数、を表示する。

エラーで処理を止めるのではなく、循環・未解決は「結果」として可視化する方針とする(デモとして「委任が破綻するとどうなるか」を見せる価値があるため)。

## 5. 画面UI

### 管理画面 (`/admin`)
- 人物パネル: 一覧表示、追加/編集/削除フォーム(名前、専門分野タグ)
- トピックパネル: 一覧表示、追加/編集/削除フォーム(タイトル、説明)
- 委任マトリクス: 行=人物、列=トピックの表。セルをクリックすると以下を選択するポップオーバーを表示:
  - 直接投票: 賛成/反対/中立のいずれか
  - 委任: 人物ドロップダウン(自分自身は選択肢から除外)
- 「結果を見る」ボタン → `/results` へ遷移

### 結果画面 (`/results`)
- トピック選択(タブまたはドロップダウン)
- 選択中トピックについて3種のビュー:
  1. 投票集計グラフ(円グラフまたは棒グラフ、賛成/反対/中立/未確定)
  2. 委任ネットワークグラフ(SVG自作の簡易力学配置。ノード=人物、矢印=委任方向、ノード色=最終stance、循環に含まれるノードは赤で強調)
  3. 直接投票 vs 委任の割合(簡単なテキスト/バー表示)

## 7. テスト方針

- `resolveDelegation.ts` は純粋関数として実装し、Vitest で単体テストを重点的に書く。カバーすべきケース:
  - 直接投票のみ
  - 1段委任
  - 多段委任(3人以上のチェーン)
  - 循環委任(2人・3人以上)の検出
  - 委任先の `Ballot` が未設定/存在しない人物への委任
- UIは主要操作(人物追加、委任設定、トピック切り替え、結果表示)を手動確認する。自動E2Eは本スコープでは行わない。

## 8. 将来の拡張

- `mechanisms/` ディレクトリに新しいメカニズム(例: `sortition/`, `quadraticFunding/`)を追加し、`App.tsx` にルートを足すだけで拡張できる構成とする。
- 人物・トピックなどの共通データモデルは、メカニズムごとに再定義せず共通化できるか、次のメカニズム追加時に再検討する。
